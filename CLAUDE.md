# Project: client-service

User and organization management service with Clerk authentication and PostgreSQL storage.

## Commands

- `npm test` — run all tests (unit + integration)
- `npm run build` — compile TypeScript + generate OpenAPI spec
- `npm run dev` — local dev server with hot reload
- `npm run generate:openapi` — regenerate openapi.json from Zod schemas
- `npm run test:unit` — run unit tests only
- `npm run test:integration` — run integration tests only
- `npm run db:generate` — generate Drizzle migration after schema change
- `npm run db:migrate` — run database migrations
- `npm run db:push` — push schema directly (dev only)

## Architecture

- `src/schemas.ts` — Zod schemas + OpenAPI registry (source of truth for validation + API docs)
- `src/routes/` — Express route handlers (`health.ts`, `users.ts`, `orgs.ts`)
- `src/middleware/auth.ts` — Clerk JWT auth (`requireAuth`) and API key auth (`requireApiKey`)
- `src/db/schema.ts` — Drizzle ORM table definitions (users, orgs)
- `src/db/index.ts` — Database connection (PostgreSQL via `postgres` driver)
- `src/instrument.ts` — Sentry initialization (must be imported first)
- `src/index.ts` — Express app setup, middleware, routes, auto-migration on startup
- `tests/` — Test files (`unit/`, `integration/`, `helpers/`)
- `openapi.json` — Auto-generated from Zod schemas, do NOT edit manually

## Conventions / invariants

- **Identifiers: internal endpoints key on the internal org UUID (`orgs.id`), NEVER the Clerk org id.** `orgs.id` is the internal UUID used as `x-org-id` across the whole platform; `orgs.external_id` holds the Clerk org id. client-service owns this mapping — resolve `external_id` from the row when an external provider (Clerk) needs the Clerk id. A `:orgId` path param is the internal UUID (validate `z.string().uuid()`).
- **No run-tracking / cost-declaration in this service.** Unlike other backend services, client-service is the identity root and does NOT use `@distribute/runs-client` (the `requireRunId` middleware was deliberately removed — see commit `eb28567`). Do NOT add run tracking or cost declaration to its routes.
- **Brand checkout status: client-service owns the (org, brand) ↔ money join, and it is DERIVED LIVE — never stored here.** `GET /internal/brands/:brandId/checkout-status` and `GET /internal/orgs/:orgId/brands/:brandId/checkout-status` (`src/lib/checkout-status.ts`) answer "has this org actually gone through checkout for this brand?". Definition, do not weaken it: CHECKED OUT = **money** (stripe-service `/internal/payment_summary/by-org/{orgId}` reports a positive gross `amount_received` — never `amount_net`: a later refund does not un-happen a checkout) **AND brand commitment** (billing-service `/internal/brands/{brandId}/daily-budget` returns a non-null `dailyBudgetCents` for that org). Stripe carries **no brand id** on any Checkout Session or PaymentIntent anywhere in the fleet, so the money leg alone cannot distinguish brands; the per-brand daily budget is the only per-brand money signal that exists, and the product writes it only in the post-payment launch step — an onboarding abandoned before paying never reaches it. A null budget stays null (billing's documented unset state) and an org with no mirrored payments stays unpaid: no default, no fallback, no local mirror. Any upstream failure is a **502**, never a defaulted "nobody paid" — a consumer must be able to tell "nobody paid" from "we could not find out".
- **Invites are UNCAPPED, and a claim is not finished until billing-service has heard about it.** An org earns the referral reward on every conversion, so there is no quota: validation rejects a code only when no org owns it, and `GET /internal/orgs/:orgId/invites/status` reports `{ signups, code }` — the old `used`/`total`/`expired` trio existed only to express the retired cap and was removed rather than left reporting a meaningless ceiling. Do not reintroduce a cap in any form (constant, config, "soft" warning). The claim itself stays idempotent per (code, invitee) and the invitee side is still recorded here; what is NOT ours is the money — client-service opens no promise and grants no credit, it only tells billing-service who referred whom (`src/lib/billing-service-client.ts` → billing's referral-claim endpoint) so billing can open the invitee's promise and remember the inviter to pay on conversion. That call is on the request path and FAILS LOUD as a **502**: a claim recorded here that never reached billing leaves a customer owed money nobody will pay, so it must never be a fire-and-forget or a swallowed error. Delivery is tracked by `invites.billing_notified_at`, written only AFTER billing acknowledges — so a repeated claim of the same pair does not notify twice, and a claim whose notification failed retries on the next (idempotent) call rather than being silently skipped. Never set that marker before the call succeeds: a crash between the two would mark a notification delivered that never was.
- **The reward-task ledger is BRONZE / SILVER / GOLD, and a completion is judged on the money CONTENT, never on a producer timestamp.** client-service owns the customer's product-reward ledger (`src/lib/reward-tasks.ts`, `GET /internal/brands/:brandId/reward-tasks`) because it is the identity root and nothing else in the fleet remembers it. Bronze `reward_funnel_observations` = what brand-service actually served for one funnel, verbatim, appended only when the money content differs from the last row (the dashboard re-reads this on every page load, so appending every response would make it a log of our HTTP traffic instead of of the customer's numbers). Silver `reward_task_states` = one canonical row per (org, offer, funnel, task). Gold `reward_task_status` = the serving view, and `reward_task_due_at()` is the ONE definition of the 30-day cadence — the read and the completion decision both go through it so "is it due" cannot come to mean two things. **brand-service's `updatedAt` is NOT a confirmation signal**: it also moves when a funnel is merely switched off or back on, so a ledger keyed on it would mark a task done that nobody did and pay for it. The discriminator is `fingerprintFunnelContent` — a sha256 over the rates, arrows, lifetime revenue and links, with `active`, `updatedAt` and `name` deliberately EXCLUDED. Do not add either toggle field to that fingerprint. The producer's timestamp is used for exactly one thing: the baseline on a FIRST sighting (provenance `producer_ts`), where it is an upper bound on the real change time, so the task comes due no earlier than it should — we never invent an earlier date to pay sooner. A funnel switched off keeps its silver row (that is what lets its clock survive the toggle) but is not served as a task.
- **Reward completions are OBSERVED ON READ — there is no background job, and adding one is a regression.** The customer is on the funnel's page when they save their numbers and the dashboard re-reads the task list immediately after, so the read that matters always happens; a sweep nobody reads would be worse than none. `GET /internal/brands/:brandId/reward-tasks` therefore mutates: it appends bronze, advances silver, records completions and pays for them inside the request. Concurrency is held by a `FOR UPDATE` on the silver row plus the unique index on (state, `due_at`) — one completion per window, whatever races.
- **A reward pays through billing-service, on the request path, fail loud, with a delivery marker — the same shape as the invite reward, not a second one.** client-service grants no credit and opens no promise: it calls billing's `POST /internal/credits/grant` with `reason: "product_task_completed"` and `completionId` = our completion row's uuid (`notifyProductTaskCompleted`). That reason RECURS, so billing keys its idempotency on (org, completionId) rather than on (org, reason) as the one-shot invite reasons do — sending no completionId is a 400 there. `reward_task_completions.billing_notified_at` is written ONLY after billing acknowledges: a failure is a **502** and leaves it NULL so the next read retries, and it is never set before the call succeeds or a crash between the two would mark a payment delivered that never was. Never make this fire-and-forget, and never cap or throttle how many tasks an org may earn.
- **Brand → org resolution uses brand-service `GET /internal/brands/all` ONLY.** It is the sole endpoint exposing the brand↔org claim edge (one row per membership; a brand claimed by N orgs yields N rows) and it is deterministic. Do NOT switch to `GET /internal/brands/{id}` or the batch `GET /internal/brands?ids=`: neither returns the owning org, and both LAZY-FILL the brand name via a platform-billed extract-fields LLM call — a status read must never trigger paid enrichment. Consequence: a brand id with zero claims returns `no_org_claims_brand`, which deliberately merges "unknown brand" with "unclaimed global brand row" (brand-service creates global brand rows without a claim). Both mean nobody can have paid on it. If brand-service ever ships a by-brand membership endpoint, swap the full-list call for it.
- **The Clerk secret comes from key-service, NEVER from this service's env.** `src/lib/clerk-client.ts` resolves it per operation via `getPlatformKey("clerk", caller)` (`src/lib/key-service-client.ts`) — there is no `CLERK_SECRET_KEY` env var and adding one back is a regression. Clerk is a shared platform secret like every other in the fleet: the dashboard app owns it in its own env and registers it into key-service at startup; backends read it from there. (That env used to live in the dashboard's Vercel project; Vercel was deleted on 2026-08-09 and app env now lives in `/root/distribute/env/` on the host — which changes where the value is set, not who owns it or where backends read it from.) The `x-caller-method` / `x-caller-path` each function passes are REQUIRED (key-service 400s without them) and record which of our routes depend on Clerk, so keep them accurate when adding a Clerk call. The client is memoized against the resolved secret, not cached unconditionally — a rotation must swap it rather than pin the dead key.
- **Outbound calls to sibling services go through `fetchWithRetry`** (`src/lib/fetch-retry.ts`). A sibling can be mid-restart when we call it — deploys are a cron running `deploy.sh` with a health check and automatic rollback, so every service has short windows where it is not accepting connections — and the request then rejects with a transient connect code on `err.cause` rather than answering. The wrapper was originally added for Neon scale-to-zero (siblings suspended after idle and the first request landed on a resuming compute); Neon is gone and nothing suspends on idle any more, but the restart window keeps the retry earning its place. Only a THROWN rejection is retried (250/500/1000ms) — a completed HTTP response, 5xx included, is the service's real answer and is returned untouched.
- **CI uses pnpm** (`pnpm install --frozen-lockfile`, `pnpm test`, `pnpm build`) — `pnpm-lock.yaml` is authoritative. A `package-lock.json` is also tracked; keep it in sync when adding deps (`npm install --package-lock-only`) even though CI ignores it.
- **Cross-service calls** follow the `<SERVICE>_SERVICE_URL` / `<SERVICE>_SERVICE_API_KEY` env convention with `x-api-key` auth (e.g. `STRIPE_SERVICE_URL` + `STRIPE_SERVICE_API_KEY` for the org-teardown → stripe-service call). New external-provider/service secrets are env vars read lazily at call time (no boot-time throw). They are set in this service's env file on the host (`/root/distribute/env/client-service.env`) — Railway is gone, so there is no `railway variables` to set them with and no `*.railway.internal` hostname to point a `<SERVICE>_SERVICE_URL` at.
- **Migrations are HAND-WRITTEN, not `drizzle-kit generate`d.** The `drizzle/meta` snapshots are stale relative to the live schema (past columns were renamed/dropped via custom SQL — `0005_external_id_rename`, `0006_remove_appid`), so `drizzle-kit generate` drops into an interactive "is X created or renamed?" prompt and would emit a bogus full-diff migration. Instead: write `drizzle/00NN_<name>.sql` by hand (idempotent `CREATE ... IF NOT EXISTS`, `--> statement-breakpoint` between statements) and append a matching entry to `drizzle/meta/_journal.json` (incrementing `idx` + `tag`). The runtime migrator (`migrate()` in `src/index.ts`) only reads `_journal.json` + the `.sql` files — snapshot JSONs are `generate`-only, so a hand-written migration applies cleanly. Verify locally against a FRESH DB (`DROP`/`CREATE DATABASE` then `drizzle-kit migrate`) — a stale `__drizzle_migrations` table causes misleading "column does not exist" replays.
- **After ANY `src/db/schema.ts` or `drizzle/` change, rebuild your LOCAL test database from the MIGRATIONS before running the suite** — `psql -d postgres -c 'DROP DATABASE IF EXISTS client_test' && psql -d postgres -c 'CREATE DATABASE client_test'`, then `CLIENT_SERVICE_DATABASE_URL=postgresql://<you>@localhost:5432/client_test?sslmode=disable npx drizzle-kit migrate`. `drizzle-kit push --force` is faster and builds tables straight from `schema.ts`, but it CANNOT create anything that exists only as SQL (see the next bullet), so a pushed database is not the one production runs. Either way, a long-lived local `client_test` keeps the OLD shape and every route touching the new column or view 500s. The failure reads like a broken handler, not a stale database — the assertion says `expected 500 to be 200` and points at your route. Integration tests are also serial (`fileParallelism: false`) and each request is a real round-trip, so a loop of N sequential claims blows vitest's 5s default long before N gets interesting: pass an explicit `{ timeout: … }` to `it.each` for anything above a handful, or assert the bulk case through a direct insert instead of N HTTP calls.
- **CI REPLAYS the migrations (`pnpm db:migrate`) — never `db:push`, and `tests/unit/ci-migrations.regression.test.ts` pins that.** `drizzle-kit push` builds tables from `schema.ts`, so it cannot create anything that exists only as SQL: the gold `reward_task_status` view and the `reward_task_due_at()` function live in `drizzle/0011_reward_task_ledger.sql` and in no TypeScript declaration. Production runs `migrate()` at boot, so a CI that pushes is testing a schema production never has — every reward-task read 500s in CI and passes locally, which reads as a flaky test rather than a missing view. Any future SQL-only artifact (view, function, trigger, partial index drizzle cannot express) inherits this: put it in a hand-written migration and leave CI on `db:migrate`.
- **A new column-level invariant (unique index, NOT NULL, CHECK) can break the `migration-0006 dedup` regression test** (`tests/integration/migration-dedup.test.ts`), which reproduces the pre-0006 schema by inserting duplicate/legacy rows. It `DROP INDEX`es the constraints that didn't exist in the 0006 era in `beforeEach` (and recreates in `afterEach`) — add any NEW unique index there too, or its transient intermediate state (0006's dedup does UPDATE-keep-then-DELETE-dupes) will trip it.
